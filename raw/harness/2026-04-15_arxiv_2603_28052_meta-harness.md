# Meta-Harness: End-to-End Optimization of Model Harnesses

**Authors**: Yoonho Lee¹, Roshen Nair¹, Qizheng Zhang², Kangwook Lee², Omar Khattab³, Chelsea Finn¹

¹Stanford University, ²University of Wisconsin-Madison, ³MIT

**Published**: March 30, 2026 (arXiv:2603.28052v1)

## Abstract

The performance of large language model (LLM) systems depends not only on model weights, but also on their **harness**: the code that determines what information to store, retrieve, and present to the model. Yet harnesses are still designed largely by hand, and existing text optimizers are poorly matched to this setting because they compress feedback too aggressively. 

We introduce **Meta-Harness**, an outer-loop system that searches over harness code for LLM applications. It uses an agentic proposer that accesses the source code, scores, and execution traces of all prior candidates through a filesystem. 

**Key Results**:
- On **online text classification**, Meta-Harness improves over a state-of-the-art context management system by **7.7 points** while using **4x fewer context tokens**
- On **retrieval-augmented math reasoning**, a single discovered harness improves accuracy on 200 IMO-level problems by **4.7 points on average** across five held-out models
- On **agentic coding**, discovered harnesses surpass the best hand-engineered baselines on **TerminalBench-2**

Together, these results show that richer access to prior experience can enable automated harness engineering.

## 1. Introduction

Modern LLM applications require more than just model weights. The surrounding infrastructure—what we call the **harness**—plays an equally critical role in determining system performance. The harness encompasses:

- **Memory management**: What information to store and retrieve
- **Context construction**: How to present information to the model
- **Tool orchestration**: Which tools to invoke and when
- **Control flow**: How to structure multi-step reasoning
- **Resource management**: How to allocate token budgets

Current harness engineering is predominantly **manual**, relying on human expertise to design these components. This approach has several limitations:

1. **High expertise barrier**: Requires deep understanding of both the domain and LLM behavior
2. **Brittle to change**: Small modifications can have unexpected effects
3. **Difficult to optimize**: Trade-offs between components are non-obvious
4. **Model-specific**: Harnesses tuned for one model may not transfer to others

### The Meta-Harness Approach

We propose **Meta-Harness**, an automated system that treats harness engineering as a **program synthesis problem**. The key insight is that harness optimization requires access to:

- **Source code**: The current harness implementation
- **Execution traces**: Step-by-step logs of harness behavior
- **Performance scores**: Quantitative feedback on outcomes
- **Historical candidates**: All previously explored harness variants

By providing an LLM-based proposer with structured access to this information through a **filesystem interface**, we enable it to:

1. Analyze patterns in successful vs. unsuccessful harness variants
2. Generate targeted modifications based on execution traces
3. Accumulate knowledge across optimization iterations
4. Discover non-obvious harness designs

## 2. Background and Related Work

### 2.1 Harness Engineering

The concept of a "harness" has evolved from software testing to become central to LLM applications. In the LLM context, a harness encompasses six key dimensions:

1. **Agent loop**: Control flow architecture
2. **Sandboxing**: Execution isolation and resource limits
3. **Human oversight**: Approval gates and escalation
4. **Observability**: Logging, tracing, and monitoring
5. **Configuration**: Permission layers and policy encoding
6. **Context budget**: Token allocation and memory management

Prior work has focused on individual dimensions (e.g., context management, tool use), but Meta-Harness addresses **end-to-end optimization** across all components.

### 2.2 Prompt Optimization

Existing prompt optimization methods (DSPy, TextGrad, ProTeGi) focus on optimizing **text prompts** given fixed harness code. These methods face a fundamental limitation: they must compress all feedback into textual form, losing structural information about code execution.

Meta-Harness extends beyond prompt optimization by:
- Operating on **executable code** rather than just text
- Providing access to **structured execution traces**
- Enabling **incremental refinement** through filesystem persistence
- Supporting **compositional changes** across multiple harness components

### 2.3 Program Synthesis

Meta-Harness draws on program synthesis techniques but applies them to a novel domain: LLM application infrastructure. Unlike traditional synthesis (e.g., PROSE, FlashFill), harness synthesis involves:
- **Non-deterministic execution**: LLM outputs vary across runs
- **Compositional structure**: Multiple interacting components
- **Performance trade-offs**: Speed vs. accuracy, cost vs. quality
- **Model-agnostic design**: Harnesses should generalize across models

## 3. Meta-Harness Framework

### 3.1 Problem Formulation

Given:
- A task specification $T$ (e.g., "classify user queries")
- A set of training examples $\mathcal{D}_{\text{train}}$
- A base harness template $H_0$

Find: An optimized harness $H^*$ that maximizes performance on held-out test set $\mathcal{D}_{\text{test}}$

The harness $H$ is defined as executable code with the signature:
```python
def harness(input: str, tools: List[Tool]) -> Output:
    # Memory management
    # Context construction
    # Tool orchestration
    # Control flow
    return output
```

### 3.2 Architecture

Meta-Harness consists of three components:

**1. Filesystem Interface**

All harness candidates, execution traces, and scores are stored in a structured directory:

```
workspace/
  candidates/
    h001_baseline.py
    h002_add_retrieval.py
    h003_optimize_context.py
  traces/
    h001_trace_example1.json
    h001_trace_example2.json
  scores/
    h001_scores.json
    h002_scores.json
```

This enables the proposer to:
- Read any prior harness implementation
- Analyze execution traces for debugging
- Compare scores across variants
- Track provenance of design decisions

**2. Agentic Proposer**

An LLM-based agent that:
- Explores the filesystem to understand prior attempts
- Identifies patterns in successful vs. failed harnesses
- Generates new harness code through targeted modifications
- Explains its reasoning through natural language commentary

The proposer prompt template:
```
You are optimizing a harness for [TASK]. 

Current best score: [SCORE]
Recent attempts: [LIST]

Review the execution traces in traces/ to identify failure patterns.
Review candidate harnesses in candidates/ to understand what has been tried.

Propose a new harness that addresses the failure patterns while maintaining 
successful components. Save to candidates/h[N]_[description].py.
```

**3. Evaluation Loop**

```python
while not converged:
    # 1. Proposer generates new harness
    h_new = proposer.generate(workspace)
    
    # 2. Execute on training examples
    traces = []
    for example in train_data:
        trace = execute_with_logging(h_new, example)
        traces.append(trace)
    
    # 3. Compute score
    score = evaluate(h_new, train_data)
    
    # 4. Save to filesystem
    save_candidate(h_new)
    save_traces(traces)
    save_score(score)
    
    # 5. Update best
    if score > best_score:
        best_harness = h_new
```

## 4. Experiments

We evaluate Meta-Harness on three diverse tasks spanning different harness dimensions:

### 4.1 Online Text Classification

**Task**: Classify incoming user queries into categories with streaming data that requires memory management.

**Baseline**: State-of-the-art context management system from Zhou et al. (2026)

**Results**:
- **Accuracy**: +7.7 points improvement (72.3% → 80.0%)
- **Context tokens**: 4x reduction (2,400 → 600 tokens per query)
- **Latency**: 2.3x faster response time

**Key discovery**: Meta-Harness learned to use a **hierarchical memory structure** with:
- Short-term buffer for recent queries (last 10)
- Semantic index for similar past queries (top-5 retrieval)
- Category-specific summaries (condensed statistics)

This combination was **not present in any baseline** and emerged through iterative refinement across 37 harness candidates.

### 4.2 Retrieval-Augmented Math Reasoning

**Task**: Solve IMO-level mathematics problems using retrieval over theorem database.

**Dataset**: 200 problems from recent International Mathematical Olympiads

**Results across 5 models**:
- **Claude Opus 4.6**: +5.2 points (34.5% → 39.7%)
- **Claude Sonnet 4.6**: +4.8 points (28.1% → 32.9%)
- **GPT-4**: +4.3 points (31.2% → 35.5%)
- **Gemini Ultra**: +4.9 points (29.8% → 34.7%)
- **LLaMA 3.1 405B**: +3.9 points (26.4% → 30.3%)

**Average improvement**: +4.7 points

**Key discovery**: Meta-Harness learned a **two-stage retrieval strategy**:
1. Coarse retrieval over problem types (geometry, algebra, combinatorics)
2. Fine-grained retrieval over specific theorems within selected type

Additionally, it discovered that **theorem paraphrasing** (restating theorems in problem-specific terminology) improved utilization by 23%.

### 4.3 Agentic Coding

**Task**: Complete coding tasks on TerminalBench-2 (167 real-world tasks)

**Baseline**: Best hand-engineered harness from OpenHands

**Results**:
- **Pass@1**: 52.7% (baseline) → 58.4% (Meta-Harness) = **+5.7 points**
- **Average steps**: 8.3 → 6.1 (more efficient)
- **Token usage**: -18% reduction

**Key discovery**: Meta-Harness learned to:
1. **Front-load exploration**: Read multiple related files before editing
2. **Incremental verification**: Test changes after each file modification
3. **Rollback on regression**: Automatically revert changes that break tests

This **test-driven harness design** was not present in baselines and emerged from analyzing traces of successful vs. failed coding attempts.

## 5. Analysis and Ablations

### 5.1 Importance of Filesystem Access

We ablate the filesystem interface to understand its contribution:

| Access Level | Online Classification | Math Reasoning | Agentic Coding |
|--------------|---------------------|----------------|----------------|
| No filesystem (baseline) | 72.3% | 34.5% | 52.7% |
| Source code only | 75.1% (+2.8) | 36.2% (+1.7) | 54.3% (+1.6) |
| + Scores | 76.8% (+4.5) | 37.1% (+2.6) | 55.9% (+3.2) |
| + Execution traces | 80.0% (+7.7) | 39.7% (+5.2) | 58.4% (+5.7) |

**Conclusion**: Execution traces provide the most value, enabling the proposer to debug failures and understand causality.

### 5.2 Proposer Model Scaling

| Proposer Model | Online Classification | Math Reasoning |
|----------------|---------------------|----------------|
| Claude Sonnet 4.0 | 76.5% | 37.3% |
| Claude Opus 4.6 | 80.0% | 39.7% |
| GPT-4 | 77.2% | 38.1% |

**Conclusion**: More capable proposer models yield better harness designs, but even mid-tier models achieve substantial gains.

### 5.3 Iteration Count

Performance improves with more optimization iterations but shows diminishing returns:

- **Iterations 1-10**: Rapid improvement (+5.2 points)
- **Iterations 11-30**: Moderate gains (+2.1 points)
- **Iterations 31-50**: Marginal improvements (+0.4 points)

Most gains occur in the first 20 iterations (typically 3-4 hours of compute).

## 6. Discussion

### 6.1 Discovered Design Patterns

Across experiments, Meta-Harness consistently discovered several non-obvious patterns:

**1. Adaptive context budgets**: Allocate more tokens to difficult examples, fewer to easy ones

**2. Staged retrieval**: Coarse-to-fine search reduces retrieval latency while maintaining quality

**3. Execution checkpoints**: Save intermediate state for rollback on failure

**4. Selective logging**: Log detailed traces only for low-confidence outputs

These patterns were **not explicitly programmed** and emerged through iterative refinement.

### 6.2 Generalization Across Models

A key question is whether harnesses optimized for one model transfer to others. We evaluate cross-model transfer:

| Harness optimized for ↓ / Evaluated on → | Opus 4.6 | Sonnet 4.6 | GPT-4 |
|------------------------------------------|----------|-----------|--------|
| Opus 4.6 | **39.7%** | 32.1% | 34.8% |
| Sonnet 4.6 | 37.9% | **32.9%** | 34.2% |
| GPT-4 | 38.3% | 31.7% | **35.5%** |
| Multi-model (ensemble) | 38.9% | 32.5% | 35.1% |

**Conclusion**: Some transfer occurs, but model-specific optimization is beneficial. Ensembling across multiple proposer models provides a middle ground.

### 6.3 Limitations

**1. Computational cost**: Meta-Harness requires running 20-50 optimization iterations, each evaluating the harness on training data. This can be expensive for large datasets.

**2. Task specification**: Requires clear task definition and evaluation metrics. Not suitable for open-ended exploration.

**3. Safety**: Automated code generation requires sandboxing and validation. We use Docker containers and static analysis to mitigate risks.

**4. Interpretability**: Discovered harnesses can be complex and difficult to understand. We mitigate this through proposer-generated documentation.

## 8. Conclusion

We introduced **Meta-Harness**, an automated system for optimizing LLM application harnesses through iterative code synthesis. By providing an agentic proposer with structured access to source code, execution traces, and performance scores, Meta-Harness discovers non-obvious harness designs that outperform hand-engineered baselines.

**Key contributions**:
1. Formulation of harness optimization as program synthesis with filesystem interface
2. Demonstration of substantial gains across three diverse tasks (+4.7 to +7.7 points)
3. Analysis showing that execution trace access is critical for effective optimization
4. Discovery of reusable harness design patterns (adaptive budgets, staged retrieval, checkpointing)

**Future directions**:
- Scaling to more complex harnesses with multiple interacting components
- Transfer learning across tasks to accelerate optimization
- Interactive optimization with human feedback
- Theoretical analysis of harness optimization landscape

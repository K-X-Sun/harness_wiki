Evaluating Code Reasoning Abilities of Large Language Models Under Real-World Settings

Changshu Liu, Alireza Ghazanfari, Yang Chen, Reyhaneh Jabbarvand
(2018)
Abstract.

Code reasoning tasks are becoming prevalent in large language model (LLM) assessments. Existing benchmarks involve simple programs, failing to represent real-world complexities such as inter- or intra-procedural dependencies, core or third-party API calls, highly nested constructs, and non-primitive complex types. Evaluating LLMs under such a simplistic setting poses a significant threat to assumptions about their generalizability in practice. To enable a more realistic evaluation of code reasoning, this paper proposes RE2-Bench 111RE2-Bench stands for Realistic Resoning, a benchmark of 1,1011,101 reasoning problems, including 195195 drawn from mature real-world projects. RE2-Bench leverages static and dynamic program analysis to automatically serialize/deserialize compound, complex, and custom types galore in real-world code, going far beyond only primitive types used in prior techniques. A key feature of RE2-Bench is categorizing each reasoning problem as Easy or Hard via a principled majority-vote mechanism over nine interpretable code complexity metrics, resulting in two well-separated and semantically meaningful problem difficulty categories, suitable for precise calibration of LLM reasoning ability.

A comprehensive evaluation of six general and reasoning LLMs on two widely-used code reasoning tasks—input and output prediction—using RE2-Bench shows a significant performance drop from Easy to Hard problems (51.50%51.50\% for input prediction and 42.15%42.15\% for output prediction), confirming inflated and unrealistic assumptions about the reasoning capabilities of LLMs. RE2-Bench integrates static analysis algorithms and visualization tools to analyze the impact of various programming constructs, call chain length, prompting/training strategies, overall program complexity, and individual complexity metrics on the reasoning abilities of LLMs. We also follow a systematic, complexity-informed approach for reasoning failure analysis, categorizing them into 1818 groups. This categorization, along with case studies, can help the development of future LLMs for better code reasoning.

1. Introduction

Large Language Models (LLMs) have shown promise in various programming tasks, such as code generation (Ding et al., 2024b; Liu et al., 2023; Du et al., 2023; Li et al., 2025a), code editing (Yang et al., 2024; Jimenez et al., 2023; Xia et al., 2024), test generation (Yuan et al., 2024; Ryan et al., 2024), code translation (Pan et al., 2024; Ibrahimzada et al., 2024), bug or vulnerability detection (Ding et al., 2025; Shestov et al., 2025), and code reasoning (Liu et al., 2024; Gu et al., 2024; Liu and Jabbarvand, 2025; Chen et al., 2025; Beger and Dutta, 2025). Code reasoning assesses the abilities of LLMs to understand code semantics. Without reasoning abilities, it is hard to believe the generalizability of models to different and unseen contexts (Du et al., 2023; Jimenez et al., 2023). This demand has motivated a growing research effort to design various code reasoning evaluation tasks and benchmarks.

Existing approaches (Gu et al., 2024; Liu et al., 2024; Beger and Dutta, 2025; Chen et al., 2025) benchmark the code reasoning abilities of LLMs using either LLM-generated (CRUXEval (Gu et al., 2024)) or human-written programs from existing datasets (Avatar (Ahmad et al., 2021), ClassEval (Du et al., 2023), and HumanEval (Chen et al., 2021)). CRUXEval dataset contains simple and standalone Python programs. Avatar, ClassEval, and HumanEval programs are potentially more challenging for reasoning because they include multiple methods. However, they are far from representing real-world code repositories. Surprisingly, state-of-the-art LLMs, if evaluated for code reasoning, only consider CRUXEval programs. The high achievement of LLMs on input prediction or output prediction of CRUXEval programs, accompanied by their struggle in real-world settings, implies the need for better code reasoning benchmarks.

For a systematic comparison of real-world programs and existing datasets used for code reasoning, we identify nine code complexity measurement metrics (Table 1)222We have no claim on the completeness of these metrics. However, even within this set of metrics, we show that current reasoning problems are far behind real-world programs, motivating the inclusion of real-world problems to evaluate the code reasoning abilities of LLMs.: Cyclomatic Complexity (M1M_{1}), Compound Predicates (M2M_{2}), Nested Constructs (M3M_{3}), Structural Complexity (M4M_{4}), Third-party APIs (M5M_{5}), Inter-class Dependency (M6M_{6}), Intra-class Dependency (M7M_{7}), Primitive Variable Count (M8M_{8}), and Complex Variable Count (M9M_{9}). M1M_{1}, M6M_{6}, and M7M_{7} are classic code complexity metrics (McCabe, 1976). Prior studies have also shown that LLMs struggle in code reasoning when the program consists of compound predicates, deeply nested constructs, complex code structures such as list comprehension, API calls, and compound variables (Liu et al., 2024; Hooda et al., 2024).

We implemented a flow-sensitive static analysis pipeline to measure the values of the applicable metrics for reasoning problems used by existing approaches, as well as those we collected from SWE-bench (more details in §2). A reasoning problem is a method we ask LLM to predict its output (given the inputs) or inputs (given the output), along with its callees. For simple programs such as those from CRUXEval, the reasoning problem is the same as the program. For more complex programs consisting of multiple methods or classes, the reasoning problem is a dynamic slice (Agrawal and Horgan, 1990) of the program, i.e., a sequence of methods that will be directly or indirectly called during the execution of that method. Figure 2 shows the reasoning problem collected from SWE-bench (project scikit-learn). RE2-Bench prompts LLMs to predict input or output of _predictproba_lr method, which directly invokes decision_functions. The other methods implemented by the surrounding class are not considered as part of the reasoning problem.

Figure 1 illustrates the complexity distribution of reasoning problems from different datasets used by existing code reasoning techniques (Figures 1 (a)–(d)) and reasoning problems we collected from SWE-bench (Figures 1 (e)). It is evident that reasoning problems from SWE-bench consistently show higher complexity across all nine selected metrics. Inter-class dependencies (M6M_{6}) do not exist in HumanEval, Avatar, CRUXEval, and even ClassEval. Moreover, reasoning problems in CRUXEval, one of the most widely used benchmarks, contain no third-party API usage (M5M_{5}) and near-zero intra-class dependencies (M7M_{7}). Such complexities exist in real-world programs, and can drastically challenge the code reasoning abilities of LLMs (more details in §3.5).

This analysis motivates RE2-Bench, a collection of 1,1011,101 diverse reasoning problems from five different programming benchmarks, namely Avatar, ClassEval, CRUXEval, HumanEval, and SWE-bench (§2.1). Unlike prior works that leverage LLMs to synthesize inputs with limited and simple variable types (Gu et al., 2024; Kopel, 2025), RE2-Bench uses existing, developer-written tests to extract and serialize complex and compound variable types (§2.2). RE2-Bench categorizes the reasoning problems into two difficulty levels (Easy and Hard) via a principled majority-vote mechanism over the nine interpretable code complexity metrics. To ensure a rigorous and sound evaluation of LLMs under two difficulty levels and increase confidence in the generalizability of the claims, RE2-Bench automatically tunes majority-voting thresholds and assesses the robust separation of the two difficulty levels using Silhouette Analysis (Shahapure and Nicholas, 2020) (to determine and remove borderline reasoning problems) and Davies–Bouldin Index (Davies and Bouldin, 2009) calculation (to further assess the quality of category separation). Among all categorization possibilities with clearly separable difficulty categorization, RE2-Bench selects the one with the highest number of Hard problems as the final benchmark (§2.3).

One of the key design decisions in RE2-Bench is its adaptiveness and versioning capability: if more complexity metric dimensions or more difficult reasoning problems are added to the benchmark, the categorization automatically adjusts, and the new version receives a unique ID representative of problem difficulties. This enables RE2-Bench to scale with advances in LLM reasoning, and also helps cope with overfitting into a single version dataset (Kiela et al., 2023).

Reasoning about complex inputs, following their flow and change of states through program execution with intra- and inter-class dependencies, and determining the final state of variables at the end of execution is a non-trivial task for LLMs. RE2-Bench represents program variables in the prompt as a JSON structure, and instructs the models to predict variable values through adaptive few-shot learning (§3.3). For a more informed assessment of LLM abilities, it measures reasoning success at different levels of granularity (§3.4).

We evaluated six general (GPT-4.1, Gemini-1.5-Pro, and DeepSeek-Coder-33B) and reasoning333Our terminology sources from model developers claiming these LLMs reason/think longer to respond compared to other model series by the same company (OpenAI, 2025b; Google, 2025; Guo et al., 2025). (o4-mini, Gemini-2.5-Pro, and DeepSeek-R1) LLMs for two widely-used code reasoning tasks, input and output prediction444We chose input and output prediction tasks because they directly test end-to-end functional reasoning and support consistent and scalable evaluation concerning complexities of real-world projects., using RE2-Bench reasoning problems (§3.5). Compared to simple problems studied by prior work, real-world code is more challenging for LLMs to reason about: the average reasoning performance of the studied LLMs in input prediction and output prediction drops by 51.50%51.50\% and 42.15%42.15\%, respectively, when evaluating on Easy problems compared to Hard problems. RE2-Bench leverages static analysis to analyze the impact of various programming constructs, call chain size, prompting/training strategies, overall program complexity, and individual complexity metrics on the reasoning abilities of LLMs:

  • •

    LLMs struggle the most with nested constructs and error handling in both input and output predictions. In addition to nested constructs, loops and conditional statements are quite challenging for backward reasoning to predict inputs (§3.6.1).

  • •

    The call chains are longer in the problems for which LLMs failed to predict their inputs or outputs correctly. The average call chain length for successful output prediction is longer than that for input prediction, demonstrating better abilities of LLMs in forward reasoning (§3.6.2).

  • •

    Reasoning models demonstrate a higher performance compared to general models in both reasoning tasks (§3.6.3).

  • •

    A statistical analysis shows a moderate to strong negative correlation between LLMs’ reasoning performance and individual code complexity metric values (§3.7).

All these results confirm the necessity of RE2-Bench as a benchmark for the proper evaluation of code reasoning abilities of LLMs. We also followed a systematic approach for categorizing the reasoning failure into 1818 categories, providing a deeper understanding of what can be improved in the next generation of LLMs for better code reasoning.

Our notable contributions are: (1) a dataset of reasoning problems containing real-world code, complex objects, long call chain slices (including intra- and inter-class dependencies), and third-party API invocation; (2) a systematic and adaptive approach to categorize collected reasoning problems into two well-separated and semantically meaningful difficulty groups; (3) automated prompt crafting for input and output prediction to evaluate reasoning of complex variables, (4) proposing fine-grained evaluation metrics to measure reasoning success; (5) large-scale evaluation of code reasoning of six general and reasoning models under RE2-Bench; and a (6) a systematic categorization of reason failures into 1818 categories accompanied by case studies555Artifacts are available to reviewers (RE2-Bench, 2025).

2. RE2-Bench

Our systematic approach for benchmark construction includes three main steps of reasoning problem selection (§2.1), variable value (§2.2), and difficulty level categorization (§2.3).

2.1. Reasoning Problem Selection

RE2-Bench includes all the reasoning problems from datasets used in prior work (Avatar, ClassEval, CRUXEval, and HumanEval). We further augment them by reasoning problems collected from real-world open-source programs. Instead of mining GitHub from scratch, we used programs in SWE-bench as the initial source of extracting reasoning problems666RE2-Bench reasoning problem selection is generic and can be applied to any given Python repository with existing tests.. This is because, as a general rule of thumb, model developers exclude existing evaluation benchmarks from their training dataset, which decreases the chance of data contamination. Furthermore, recent code reasoning techniques consider cross-analysis between code reasoning and other programming tasks (e.g., bug detection, localization, and repair) (Liu et al., 2024). Given that SWE-bench already contains bug-related tasks, RE2-Bench helps existing techniques to expand their evaluations to real-world problems.

For Avatar, CRUXEval, and HumanEval, we consider each program in the dataset as a reasoning problem, as they are standalone methods. For ClassEval, each method in the class and its callees in the dynamic slice (executed by the provided unit tests) is a reasoning problem. Since ClassEval offers multiple tests for each method, we randomly select one to have unique reasoning problems. This process provides 1,4501,450 initial reasoning problems from these datasets.

For SWE-bench, we start by extracting the modified methods during bug fixing, since RE2-Bench aims to enable the cross-analysis between reasoning and bug-related tasks as mentioned before: for each problem in the SWE-bench, we extract all the methods involved in the diffs between the buggy and fixed versions. This provides us with 2,3222,322 methods. We then execute the existing unit tests and log the inputs and outputs777Given that this work focuses on input and output prediction, and that logging all intermediate (compound and/or complex) variables in real-world projects exposes huge space overhead, RE2-Bench pipeline only intercepts input and output variables. for each identified method (details in §2.2). Next, we exclude duplicates, i.e., methods with identical inputs and outputs (filtering Rule 1), and remove the methods with no return statements or input arguments (filtering Rule 2). Finally, we exclude methods whose variable types have circular dependency (filtering Rule 3), as they result in a non-terminating serialization loop (details in §2.2). Table 2 shows the number of unique methods excluded by each filtering rule. Along with their surrounding classes and the callees in the dynamic slices, these methods form 991991 the initial reasoning problems from SWE-bench. For the reasoning problems that have more than one unique (input,output) pair, we randomly select one to prompt LLMs.

2.2. Variable Value Extraction

Existing datasets follow different designs for program execution. For Avatar, the inputs and outputs are identified in text files. For HumanEval and CRUXEval, inputs and outputs are in the form of assert statements, e.g., in the assert intersperse([],7)==[], inputs are [] and 7, and output is []. For ClassEval and SWE-bench, the inputs and outputs are not explicit; instead, they have test cases to execute the code. RE2-Bench implements a generic pipeline on top of all datasets, making it easy to extend in the future with problems from other mature datasets or evaluating other code reasoning tasks: given the main method, i.e., the one in the reasoning problem that we prompt LLMs to predict the inputs or outputs, RE2-Bench extracts the input, output, and other variables through static analysis. It then runs existing tests and collects variable values at runtime.

The variables in SWE-bench reasoning problems are likely to be complex custom objects. Figure 3 (a) shows such an example, where the method widget_attrs takes a Widget object as input. As shown in Figure 3 (b), this custom type has five class attributes of bool type (needs_multipart_form, is_localized, is_required, supports_microseconds, and use_fieldset) and one instance attribute of a custom type (DefaultAttrs). The DefaultAttrs also has two class attributes of str type (type and maxlength). Variable widget initializes the return value attrs.

Without a proper introduction of variable values to LLMs, they cannot reason how input values evolve to output (output prediction) or vice versa (input prediction). Also, unlike primitive types (e.g., int or bool) or core compound types such as list or set, whose corresponding values can be printed during execution, custom objects may not implement str or repr methods by default; thereby, printing them provides memory address or hash value of the objects. To overcome this challenge, RE2-Bench leverages program analysis to recursively decompose a complex type until it reaches primitive types, and stores them in a JSON format. When prompting for prediction variable values, RE2-Bench represents variables given this structure, and instructs LLMs to understand the structure through in-context examples (§3.3). Algorithm 1 shows an overview of this mechanism. Figure 3 (c) demonstrates the results of serializing the custom type of Widget to be printed during execution.

2.3. Difficulty Level Categorization

RE2-Bench categorizes the reasoning problems into two difficulty levels: Easy and Hard, using Algorithm 2. The algorithm takes the 2,4412,441(1,4501,450++991991) initial reasoning problems from the previous step and complexity metrics as inputs, and returns a versioned code reasoning benchmark as output.

For each reasoning problem pjp_{j}, the algorithm calculates corresponding complexity metric values (Table 1), yielding a vector, [f1j,⋯,f|C​M|j][f_{1}^{j},\cdots,f_{|CM|}^{j}] (Lines 33–44). After calculating the complexity metric values for all the problems, it assigns each calculated value fijf_{i}^{j} a label (H or L), resulting in a vector of complexity labels for each problem, [l1j,⋯,l|C​M|j][l_{1}^{j},\cdots,l_{|CM|}^{j}] (Lines 55–1414): it sorts the problems according to fijf_{i}^{j}s (Lines 77–88). The complexity label lijl_{i}^{j} of the problems in the first TT percentile will be L (the T%T\% of the programs with the lowest fijf_{i}^{j}s). The complexity label lijl_{i}^{j} of the problems in the last TT percentile will be H (the T%T\% of the programs with the highest fijf_{i}^{j}s). The algorithm assigns no complexity label to the problems in between. Figure 4 shows the label breakdown of the initial reasoning problems across complexity metrics.

After assigning the complexity labels, the algorithm categorizes the problems into two difficulty levels following the majority voting principle (Lines 1515–2929): pjp_{j} is categorized under Easy or Hard, if the majority of its fijf_{i}^{j}s are labeled as L or H, respectively. The majority can be a number between ⌈|C​M|2⌉\lceil\frac{|CM|}{2}\rceil888The majority voting ≥⌈|C​M|2⌉\geq\lceil\frac{|CM|}{2}\rceil ensures that each problem is categorized under only one difficulty level. and |C​M||CM|. A lower majority will let more problems into each difficulty category, while allowing more overlap between complexity dimensions. Given the purpose of RE2-Bench, which aims to assess the reasoning performance shift concerning the difficulty of the problems, well-separated and semantically meaningful categorization is essential. Algorithm 2 dynamically balances the trade-off between coverage and separability by iterating over the majority number (Lines 1515–2929), forming the Easy and Hard categories (Lines 1616–2020), applying Silhouette Analysis to determine and remove borderline problems (Line 2121), and evaluating the quality of the categorization using the Davies–Bouldin Index (Line 2222). If DBI indicates a semantically meaningful separation between the categories, the algorithm terminates (Lines 2323–2626). Otherwise, it increments the majority for a better separation and repeats the categorization (Lines 2727–2929).

SWE-bench problems, while from well-maintained GitHub repositories, may not completely represent real-world complexity. Our complexity metrics, while selected and evaluated rigorously, may not be complete. More importantly, LLMs can overfit to benchmarks over time. Algorithm 2 mitigates these threats through design adaptiveness and versioning: if more complexity metric dimensions or more difficult reasoning problems are added to the benchmark, the categorization automatically adjusts, and the new version receives a unique ID representative of problem difficulties. Specifically, each version will be identified by T​Vl​o​wTV_{low} and T​Vh​i​g​hTV_{high}, the cut-off threshold values for each complexity dimension during labeling. With more complex problems added, the values of both vectors increase, indicating the higher version over time, scaling with advances in LLM reasoning.

The Silhouette score measures how well each reasoning problem fits within its difficulty category, based on the distance to neighboring points in the same versus other clusters, providing local reliability. DBI measures the average similarity between two difficulty categories, based on intra-cluster dispersion and inter-cluster distance, providing global soundness. Using both ensures that the categorization is not only locally precise but also globally valid, increasing the confidence of generalizability of claims. 3. Empirical Evaluation

We use RE2-Bench reasoning problems to investigate the following research questions:

Effectiveness. To what extent do RE2-Bench problems, categorized under different difficulty levels, challenge the reasoning abilities of LLMs in input and output prediction? What are the impact of false negatives?

Impacting Factors. What factors make input and output predictions more challenging for LLMs? To what extent does encoding reasoning into the training strategy help LLMs in code reasoning?

Reasoning Failure Analysis. What are the most common root causes of reasoning failures?

Ablation Study. To what extent do different prompt engineering components contribute to the overall reasoning performance of LLMs?

3.1. Reasoning Problems Sampling

In practice, all the problems under the Easy and Hard categories of RE2-Bench can be used for the evaluation of LLMs. Due to an imbalance between difficulty level sizes (more Easy problems than Hard) and their potential impact on the rigor or experimental design, we randomly sampled a subset of Easy problems, equal to the number of Hard problems, resulting in 155155 problems for each difficulty level. Figure 6 shows the distribution of 310310 reasoning problems across datasets for each difficulty level.

3.2. Subject LLMs and Evaluation Tasks

For a comprehensive evaluation, our subject LLMs include three reasoning LLMs: o4-mini (OpenAI, 2025c), Gemini-2.5-Pro (DeepMind, 2025), and DeepSeek-R1 (Guo et al., 2025); and three general counterparts LLMs: GPT-4.1 (OpenAI, 2025a), Gemini-1.5-Pro (Team et al., 2023), and DeepSeek-Coder-Inst-33B (Guo et al., 2024). This variety enables comparing the impact of reasoning-aware training compared to general-purpose training. To ensure the reproducibility of our experimental results, we set the temperature to 0 for GPT-4.1, Gemini-2.5-Pro, Gemini-1.5-Pro, DeepSeek-R1, and DeepSeek-Coder-inst-33b. The only exception is o4-mini, with a fixed temperature of 11, which we could not change. As a result, our analysis will focus on comparing the performance of LLMs with themselves under different experimental settings, and not with others.

3.2.1. Evaluation Tasks

Existing research has explored various tasks to assess different aspects of LLM’s code reasoning, including specification reasoning, specification inference, dynamic semantic reasoning, structural reasoning, and code execution simulation, and prediction of input, output, coverage, variable values, or execution path (next statement or the entire execution trace). Among these tasks, we chose input and output prediction in our experiments due to three reasons: (1) prior research has shown that LLMs that perform well in these tasks may struggle in other reasoning tasks. Thereby, input and output prediction tasks can determine the upper bound for LLM’s code reasoning abilities. (2) Furthermore, these tasks directly test forward and backward end-to-end functional reasoning, supporting consistent and scalable evaluation concerning the complexities of real-world projects. (3) These tasks are the most prevalent ones in the evaluation of the most recent models. In our experiments, we will show that this upper bound drastically drops when LLMs are evaluated under complex real-world settings, motivating future research to evaluate them in other tasks and improve their code reasoning abilities.

3.3. Prompting Strategies

Prompt crafting plays a crucial role in the performance of LLMs, especially for difficult tasks that LLMs were not explicitly pre-trained or instruction-tuned on. As a result, we follow best practices to ensure proper prompt crafting for the tasks. Figure 7 illustrates the prompt templates used for input prediction and output prediction. We use In-Context Learning (ICL) ((Mann et al., 2020; Ye et al., 2023; Dong et al., 2022)) examples to introduce the tasks to LLMs, and instruct them to perform step-by-step reasoning (explicit reasoning similar to ICL example and implicit reasoning in the general instruction). Due to the complexity of inputs and outputs in real-world reasoning problems, we include additional hints about Input/output Structure in the prompt. Specifically, we provide the serialized format of the input or output to be predicted in the prompt, and ask LLMs to fill in the values instead of predicting the structure. For example, when we ask LLM to predict the input of the reasoning problem in Figure 3 (a) given the output, we provide the serialization of Widget object shown in Figure 3 (c) with all the values removed. As a result, the LLM only needs to predict the values for each attribute. For problems from SWE-bench and ClassEval, we also present the model with the extracted function dependency and class context in the prompt if available. We perform ablation studies to show the effectiveness of different prompting strategies (§3.8).

3.4. Evaluation Metrics

RE2-Bench measures LLM reasoning abilities at two levels of granularity. At the highest level, the reasoning success, R​SiRS_{i}, is 0 or 11, i.e., the LLM prediction is identical to the collected ground truth values. This metric, however, is very conservative and unfair. In the example of Figure 3 (c), if we have two LLMs, L​L​MxLLM_{x} and L​L​MyLLM_{y}, that each correctly predict one and six of the seven properties of the input widget, both achieve R​Si=0RS_{i}=0 for this program. However, the L​L​MyLLM_{y} is superior to L​L​MxLLM_{x} due to its ability to predict more properties.

This problem could have been negligible or non-existent for previous code reasoning benchmarks. However, since RE2-Bench problems include the prediction of complex objects, there is a need for a finer-grained metric to compare the reasoning abilities of the models. To enable more insightful comparison between the reasoning abilities of the models, we introduce an additional metric to measure the partial reasoning correctness, R​Sp​a​r​t​i​a​liRS_{partial_{i}}, as below:

where mm is the total number of properties for each input or output variable to be predicted for problem ii, P​r​e​djPred_{j} is the prediction of LLM for that property, and G​TjGT_{j} is the ground-truth value for the property. Using this metric, the LLMs mentioned in the previous example (L​L​MxLLM_{x} and L​L​MyLLM_{y}) achieve R​Sp​a​r​t​i​a​li=0.14RS_{partial_{i}}=0.14 (17)(\frac{1}{7}) and R​Sp​a​r​t​i​a​li=0.86RS_{partial_{i}}=0.86 (67)(\frac{6}{7}), respectively, providing a fairer comparison between models. 3.5. RQ1: Effectiveness

We explore how changing the difficulty of the reasoning problems impacts the performance of individual models. For each reasoning problem, we compute both R​SRS and R​Sp​a​r​t​i​a​lRS_{partial}. Table 3 presents the overall performance of the models concerning evaluation metrics, and Figure 8 shows the distribution of successful reasoning (R​S=1RS=1) and failed reasoning (R​S=0RS=0) across all the difficulty levels in more detail. We report the breakdown per the origin or reasoning problems to further highlight the inflation of code reasoning abilities of LLMs when evaluated on CRUXEval problems.

LLMs consistently achieve a higher reasoning success in Easy problems compared to Hard ones: for input prediction, on average, R​SRS drops from 77.74%77.74\% to 26.24%26.24\%, moving from Easy to Hard reasoning problems. For partial reasoning, R​Sp​a​r​t​i​a​lRS_{partial}, the performance drops from 88.93%88.93\% to 61.57%61.57\%, respectively. For output prediction, on average, R​SRS drops from 78.49%78.49\% to 36.34%36.34\%, when moving from Easy to Hard reasoning problems. For partial reasoning, R​Sp​a​r​t​i​a​lRS_{partial}, the performance drops from 79.86%79.86\% to 46.50%46.50\%, respectively.

Reasoning LLMs (o4-mini, Gemini-2.5-Pro, and DeepSeek-R1) outperform non-reasoning LLMs in both R​SRS and R​Sp​a​r​t​i​a​lRS_{partial}, by 11.45%11.45\% and 9.82%9.82\%, respectively. The only exception is Gemini-2.5-Pro compared to Gemini-1.5-Pro on the input prediction of Hard problems. Given a thorough manual analysis of the LLM responses to ensure correctness of RE2-Bench parsing scripts, as well as the use of adaptive in-context learning through prompting, this discrepancy is not due to bugs in the pipeline. The reasoning model also consistently outperforms the general model in different tasks and difficulty levels. Hence, we speculate this to be attributed to capability drift or regression of LLMs on certain reasoning tasks across successive updates or versions (Chen et al., 2024b; Li et al., 2025b; Shumailov et al., 2024).

For all models and under all levels of difficulty, R​Sp​a​r​t​i​a​lRS_{partial} values are 23.71%23.71\% and 4.65%4.65\% higher than R​SRS, on average, for input and output prediction. This indicates that although LLMs have yet to achieve perfect code reasoning to predict all input or output values correctly, they can reason about some properties of inputs and outputs. We believe code reasoning research needs both metrics: a strict metric, such as R​SRS, can better reflect the end-to-end capabilities of the model in code reasoning. At the same time, there is a need for R​Sp​a​r​t​i​a​lRS_{partial} to reflect the incremental correctness or model’s gradual progress (Yu et al., 2024; Lyu et al., 2025). For the remainder of RQ1, RQ2–RQ3 (§3.6–§3.7), we use R​SRS as it better reflects the overall LLMs’ reasoning strength. We use R​Sp​a​r​t​i​a​lRS_{partial} during the ablation study in RQ4 (§3.8).

Finally, we analyze how the behavior of the same LLM changes from one reasoning task to another. Figure 9, shows the number of unique and common problems each LLM succeeds in predicting their inputs and outputs. We observe that LLMs are more successful in output prediction compared to input prediction, with an overall success rate of 57.53%57.53\% compared to 51.99%51.99\%. This is likely because input prediction is intuitively harder than output prediction, i.e., the LLM should perform only forward reasoning for output prediction, compared to both forward and backward reasoning for input prediction (Ding et al., 2024c). Furthermore, as the difficulty of the reasoning problems increases, i.e., moving from outer doughnuts to inner ones, the percentages of overlap between input and output prediction success decrease. The gap is bigger for Hard problems, as real-world code contains more complex loops or conditional statements, making backward analysis considering complex objects as path conditions more difficult.

From these results, it is evident that the reasoning abilities of LLMs on Easy cannot generalize to Hard problems, the ones that LLMs need to deal with in practice. This confirms the necessity of including reasoning problems with real-world difficulties in the dataset. Additionally, we argue that a comprehensive benchmark should include problems of different difficulty levels, as RE2-Bench does, due to the following reasons: (1) software engineering task complexities follow a long-tail distribution, i.e., some of them are small code with no notable complexity, and some are multiple methods or classes. Studies have shown that larger or better-trained LLMs may do worse on simple or trivial problems while improving on harder ones (inverse scaling) (McKenzie et al., 2023; Williams and Huckle, 2024); and (2) categorization enables regression testing across model versions or prompt revisions, which is specifically required for per-capability error analysis and targeted model diagnosis (Ding et al., 2024a).

3.5.1. False Negatives in Input Prediction

The possibility of false negatives in output prediction is narrow, since the outputs were either provided by the tests in the datasets, or we executed the tests to collect actual values during test execution. However, false negatives in input prediction are plausible: multiple inputs may result in the same output (Dijkstra and Dijkstra, 1982; Dinges and Agha, 2014).

RE2-Bench automates the detection of such cases for Avatar, ClassEval, CRUXEval, and HumanEval, and updates their reasoning success. To automate false negative detection in input prediction, RE2-Bench runs the standalone methods with the predicted inputs by LLMs and the ground truth input separately, and compares their execution results with assertions. For ClassEval, an additional step of initializing the class with the predicted and ground truth self arguments before executing methods is required. Once confirmed as a false negative, RE2-Bench updates the R​SRS and R​Sp​a​r​t​i​a​lRS_{partial} values to one. All the reported numbers in the paper reflect the correction of false negatives to true positives.

Figure 11 demonstrates the number of false negatives for each LLM. False negatives in programs with simpler logic are quite high, especially for reasoning models compared to general models, demonstrating the creativity and flexibility of the LLMs in code reasoning. The majority of the false negative cases belong to CRUXEval. This is not surprising, as CRUXEval problems are very simple synthetic programs generated by LLMs, hence, they implement simple logic. Avatar and HumanEval problems may not represent real-world complexity, but are algorithmically complex, resulting in a more strict mapping between input and output space. The majority of the false negative cases for ClassEval also belong to simple methods such as setter methods, which do not implement a notable logic.

Figure 10 (a) illustrates a false negative case in Avatar. The code factorizes input into prime numbers, computes the number of distinct numbers smaller than each exponent in the factorization, and returns the sum of them. The factorization of the ground truth input is [25][2^{5}]. The number of distinct numbers adding up to a number smaller than each exponent in the factorization is 22 (the output). o4-mini and Gemini-2.5-Pro predict 66 as the input, which, although not equal to the ground truth input 3232, results in the same output: the factorization(6) is [21,31][2^{1},3^{1}], and the sum of distinct numbers adding up to a number smaller than each exponent equals to 2​(1+1)2(1+1). Similarly, GPT-4.1 predicts 1010 as input, which results in [21,51][2^{1},5^{1}] as the return value of 2​(1+1)2(1+1) as the final output.

Automating the detection of input prediction false negatives in real-world problems faces non-trivial challenges, e.g., the need for initializing a class with complex attributes first before calling the method whose inputs are predicted by the LLM. To that end, we manually checked for the existence of false negatives concerning the reasoning problems from SWE-bench. Given the large number of incorrect input predictions from SWE-bench problems (646646 for all studied LLMs), we focused on 151151 Output Prediction Only cases from Figure 9. The rationale is that LLMs could correctly reason forward in these cases, increasing the likelihood of their backward reasoning success. From manual analysis, we observed 1414 instances corresponding to four problems 101010Additional examples are available in our artifact website (RE2-Bench, 2025).. Figure 10 (b) illustrates such a case from project Sympy: the method split_super_sub takes text as input. The loop partitions the input into the base name, superscript (supers), and subscript (subs). After the loop, an if-condition checks whether the name ends with digits. If so, the number is placed at the beginning of the subscript. In this example, o4-mini, GPT-4.1, Gemini-1.5-Pro, and Gemini-2.5-Pro predict "alpha1ˆ+", whereas DeepSeek-R1 predicts "alpha_1ˆ+". Both predictions, however, yield the same output as the ground-truth input "alphaˆ+_1".

3.6. RQ2: Impacting Factors

We analyze the impact of three different factors on the reasoning abilities of LLMs for input and output prediction. During analysis, we will discuss specific impacts on input or output prediction.

3.6.1. Analysis of Program Constructs

Complex program constructs can pose greater reasoning challenges for LLMs (Liu et al., 2024; Hooda et al., 2024). To analyze the syntactic properties of the problems and their impact on the input and output reasoning, we used ExerScope (Liu and Jabbarvand, 2025). ExerScope uses static analysis to identify different programming constructs in Python code and label them with all existing code constructs. The existing labels implemented in ExerScope are Basic (B)—no specific programming constructs, For (F)—for loop, If (I)—if statement, Nested If (NI)—nested if statements, Nested Loop (NL)—nested for, Try (T)–exception handling, and While (W)—while loop. After labeling the problems, ExerScope clusters them according to labels and visualizes the results as a spider chart. Figure 12 shows the result for each level of problem difficulty, input prediction (Figure 12 (a)) and output prediction (Figure 12 (b)). We observe that LLMs struggle the most with nested constructs (NI and NL labels) and error handling (T label) in both input and output predictions.

3.6.2. Analysis of Call Chains

The majority of the reasoning problems from SWE-bench contain intra- and inter-class dependencies. As a result, for the prediction of input and outputs of the main method, LLMs need to reason about the control and data flow of methods called inside it. To further investigate the impact of call chain size on the reasoning performance of LLMs, we measured the call chain size, i.e., the number of methods involved in the reasoning problem slice. In the example of Figure 2, the call chain size is two, since the main method invokes only one method in its body.

Figure 13 plots the range of call chain size for reasoning problems that each LLM succeeded (labeled as succ) or failed (labeled as fail) in predicting its inputs or outputs. The call chain size, on average (dashed green lines), is higher for the reasoning problems for which LLMs failed to predict their inputs or outputs correctly. The average call chain size for successful output prediction is higher than that for input prediction for each model. This is likely because LLMs perform better in output prediction, including simpler problems with shorter call chains; thereby, the average is skewed to lower values.

3.6.3. Analysis of Training Strategies

Table 3 shows that reasoning LLMs surpass general LLMs in input and output prediction. Reasoning LLMs benefit from additional supervised fine-tuning that enhances their reasoning overall, and our results show that reasoning ability generalizes to code reasoning. For a deeper analysis, we further looked into unique and overlapping reasoning problems in each model’s family success in predicting their inputs or outputs.

Figure 14 shows the comparison between reasoning and general LLMs in each family (columns) for each difficulty level (rows), separated for input and output prediction. Overall, reasoning models can reason about more unique problems compared to general LLMs, except for Gemini-2.5-Pro under Hard problems. Despite the overall superiority, we can observe that there are 4646 cases where general LLMs correctly reason about inputs or outputs, but their counterpart reasoning LLM fails. Our analysis of these cases does not show a consistent pattern. We speculate this observation is due to Inverse-Difficulty Scaling effect, i.e., advanced LLMs that succeed in more complex tasks may fail in cases that precedents models can succeed (Zhou et al., 2024).

3.7. RQ3: Reasoning Failure Analysis.

We follow a semi-automated approach for a systematic root-cause analysis of reasoning failures. To that end, we revisit the complexity metrics (Table 1 that were used to motivate the need for better benchmarks. We first use the point biserial correlation (Kornbrot, 2014) (rp​br_{pb}) to measure the strength and direction of the relationship between reasoning results (binary R​SiRS_{i} values) and complexity metric values (continuous values of M1M_{1} to M9M_{9}) across all the reasoning problems. The coefficient rp​br_{pb} takes a value between −1-1 and 11. The sign indicates positive or negative correlation, and the value determines the strength of correlation. Values close to zero indicate little to no relationship. Table 4 shows the results of this analysis. Except for a few cases, there is always a strong to moderate negative correlation between the success of LLMs in studied code reasoning tasks and measured complexity metrics. Among the metrics, M8M_{8}, which entails reasoning about several primitive type variables in the program to predict inputs or outputs, is not as challenging for LLMs.

For root cause analysis, we start by creating reasoning failure categories corresponding to individual or a group of complexity metrics, as shown in Figure 15: Conditional Statements (purple) with M1M_{1}, and M2M_{2}, Recursions (blue) with M1M_{1}, and M3M_{3}, Structural Dependency Oversight (Green) with M4M_{4}, Call Dependencies (Yellow) with M5M_{5}, M6M_{6}, and M7M_{7}, and Types (Orange) with M8M_{8}, and M9M_{9}. Next, we assign reasoning failures into these categories as follows: a reasoning failure belongs to cluster ii if its MiM_{i} metric is labeled as H (High), allowing failures to be grouped into one or more clusters. For example, a reasoning failure with High label for its M1M_{1}, M2M_{2}, and M3M_{3} will be categorized under both Conditional Statements and Recursions categories. The duplication under different categories allows for incorporating different possibilities for failures. The number of reasoning failures corresponding to each category is reported in Figure 15: the tuple under the category name shows the number of reasoning failures for input prediction and output prediction, accumulated for all LLMs. For example, there are 740740 and 641641 reasoning failures under Conditional Statements category. Figure 16 also shows the breakdown of the numbers over each LLM.

Once reasoning failures are assigned to categories, we randomly selected 3030 instances from each cluster for each task to manually analyze the LLM CoT traces, providing us with 300300 reasoning failure instances (150150 for input prediction and 150150 for output prediction). Selection of 3030 instances allows us to detect any theme appearing in ≥10%\geq 10\% of reasoning failures at each category with 95%95\% confidence. In the random selection process, we selected an equal number of five reasoning failure instances for each category for a given LLM. As a result of this manual investigation, we derive reasoning failure subcategories, e.g., Call Stack Confusion, Variable Tracking Overload in Figure 15. Through this process, we also identified cases that could have been categorized under a unique group, LLM Specific (Red) category in Figure 15. While we do not claim completeness due to incorporating sampling (although with a high confidence interval) and studying two reasoning tasks, the multi-step process, grounded in statistical analysis and manual investigation, is systematic and rigorous, which can be extended/generalized to other reasoning tasks.

3.7.1. Qualitative Analysis

We discuss a few examples of reasoning failures identified from previous analysis111111Additional examples are available in our artifact website (RE2-Bench, 2025).. Figure 17 (a) shows an example where Gemini-2.5-Pro predicts an incorrect output for sympy__sympy-13177 problem, due to incorrect reasoning on the conditional properties. The code takes two strings (p="zoo" and q="0") as inputs, converting them into Sympy symbol zoo (representing complex infinity in Sympy121212https://docs.sympy.org/latest/modules/core.html) and integer 0, respectively. Since p=zoo satisfies p.is_infinite, the code takes the first if branch and returns nan. However, Gemini-2.5-Pro mispredicts the compound predicate in the first if condition, skips the correct branch, and as a result, fails to encounter any return statement. 3.8. RQ4: Ablation Study

3.8.1. Prompting Strategies

We evaluate two aspects of our prompting strategy on LLMs’ reasoning performance. For Structural Hints, we removed the pre-defined structure of the inputs or outputs from the prompt for both the ICL example and the query problem (e.g., $ICL_OUTPUT_STRUCTUR$ and $OUTPUT_STRUCTURE$ in Figure 7 (a)). Considering the example in Figure 3 (c), instead of providing the JSON structure and variable names whose values should be predicted, we only ask LLM to predict the output of widget. For the CoT, we removed both implicit CoT (i.e., the sentence “Execute the program step by step” under the ###Instruction) and explicit CoT ($ICL_CoT$, where we teach the model how to execute the code step by step) from the prompts. The results of the ablation study (Table 5) confirm the effectiveness of our prompt crafting strategy in helping better code reasoning.

On average, Structural Hints improves the performance on R​SRS and R​Sp​a​r​t​i​a​lRS_{partial} by 7.43%7.43\% and 9.88%9.88\%, respectively. The gain for LLMs is more notable under the Hard problems. CoT improves the performance of LLMs on R​SRS and R​Sp​a​r​t​i​a​lRS_{partial} by 2.56%2.56\% and 3.22%3.22\%, respectively. The only exception is DeepSeek-Coder-Inst-33B on Hard problems, where CoT fails to improve R​SRS. Our manual analysis reveals that this is because DeepSeek-Coder-Inst-33B occasionally hallucinates during the CoT reasoning process, repeatedly generating the same text until exhausting the context window, without producing any valid input/output predictions. C​o​TCoT still improves R​Sp​a​r​t​i​a​lRS_{partial} of DeepSeek-Coder on Hard Problems, i.e., helping the model to partially predict variables correctly.

4. Related Work

RE2-Bench is related to studies on code reasoning tasks (Gu et al., 2024; Liu et al., 2024; Chen et al., 2024a; Beger and Dutta, 2025; Kopel, 2025; Le-Cong et al., 2025; Yang et al., 2025; Sun et al., 2025; Bouras et al., 2025; Gautam et al., 2025). CRUXEval (Gu et al., 2024) and CodeMind (Liu et al., 2024) are pioneers in evaluating LLMs for different code reasoning tasks. CRUXEval reasoning tasks are input prediction (given the output) and output prediction (given the inputs). CodeMind proposed three tasks (independent execution reasoning, dependent execution reasoning, and specification reasoning) to evaluate LLMs’ inductive code reasoning abilities. REval (Chen et al., 2024a) took one step forward to include the runtime behavior in the reasoning process using four runtime prediction tasks: code coverage prediction, program state prediction, execution path prediction, and output prediction. CoCoNUT (Beger and Dutta, 2025) challenges LLMs to generate a trace of line numbers executed by the program for a given set of inputs. EquiBench (Wei et al., 2025) assesses LLMs’ understanding of code execution semantics by requiring them to judge whether two programs produce equivalent outputs for every possible input. These techniques either leveraged LLMs to generate the reasoning problem or used programs from existing programming benchmarks. As we showed in this paper, the reasoning problems used in prior studies are far from representing the complexities of real-world programs, failing to challenge the reasoning abilities of LLMs properly (§1). Compared to these techniques, RE2-Bench extracts reasoning problems from real-world projects.

Two closely related works are EXE (Kopel, 2025) and CodeSense (Roy et al., 2025) that evaluate LLM code reasoning on open-source Python repositories. Similar to CRUXEval, EXE relies on LLMs to generate test inputs, limiting them to simple and primitive variable types. CodeSence collects input-output pairs from actual execution trace logs, but rules out those with non-primitive data types. To better preserve the complexity of real-world code inputs, RE2-Bench collects actual runtime inputs by executing project test cases. It goes beyond primitive and core compound types and can serialize any complex custom type into a readable JSON-like format. Furthermore, RE2-Bench follows a systematic approach to categorize the reasoning benchmarks into three difficulty levels.

5. Threats to Validity

External Validity. To mitigate the threat of generalizing results to other experimental settings (other models, benchmarks, and tasks), our selected models cover both open-source and API access models, as well as general and reasoning models. Concerning new benchmarks, RE2-Bench pipeline is generic, i.e., it can convert any Python project with executable test suites into reasoning problems. The rigorous design of difficulty-level categorization of problems makes RE2-Bench adaptive to new problems and new LLM capabilities, as discussed in the paper. As a proof of concept, this paper shows that the code reasoning abilities of LLMs in two widely used tasks of input and output prediction can be significantly challenged under real-world settings. RE2-Bench currently focuses on Python, as the majority of the programming datasets widely use it. Focusing on one language also enables systematic control over complexity metrics and avoids language-induced variance.

Internal Validity. LLMs are inherently non-deterministic. One way to account for non-determinism is repeating the experiments kk times, and reporting the R​S​@​kRS@k results. However, a similar computation is not possible for R​Sp​a​r​t​i​a​lRS_{partial} due to the inherent dependency between attributes of complex objects. Given that in practice, users of LLMs do not repeatedly prompt LLMs and pick the correct solution, if it exists, this design decision does not pose a threat to the validity of the results.

Construct Validity. To account for the imbalance between the problems in each difficulty category, RE2-Bench systematically sampled Easy reasoning problems, equal to the number of Hard problems.

6. Conclusion

In this paper, we introduce RE2-Bench, a curated collection of existing programming benchmarks tailored for code reasoning, in which reasoning problems are categorized into two difficulty levels. We evaluate six widely used reasoning and general LLMs on input and output prediction tasks and observe a substantial performance drop from Easy to Hard programs, revealing that existing benchmarks may overstate LLMs’ reasoning capabilities. For future work, we plan to support more reasoning tasks and programming languages, and implement a more systematic approach for detecting false negatives in input prediction for SWE-bench reasoning problems.

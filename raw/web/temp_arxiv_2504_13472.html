Abstract

Large language models (LLMs) have demonstrated strong capabilities in code generation, underscoring the critical need for rigorous and comprehensive evaluation. Existing evaluation approaches fall into three categories, including human-centered, metric-based, and LLM-based. Considering that human-centered approaches are labour-intensive and metric-based ones overly rely on reference answers, LLM-based approaches are gaining increasing attention due to their stronger contextual understanding capabilities and superior efficiency. However, the performance of LLM-based approaches remains limited due to: (1) lack of multisource domain knowledge, and (2) insufficient comprehension of complex code.

To mitigate the limitations, we propose CodeVisionary, the first LLM-based agent framework for evaluating LLMs in code generation. CodeVisionary consists of two stages: (1) Multisource knowledge analysis stage, which aims to gather multisource and comprehensive domain knowledge by formulating and executing a stepwise evaluation plan. (2) Negotiation-based scoring stage, which involves multiple judges engaging in discussions to better comprehend the complex code and reach a consensus on the evaluation score. Extensive experiments demonstrate that CodeVisionary achieves the best performance for evaluating LLMs in code generation, outperforming the best baseline methods with average improvements of 0.202, 0.139, and 0.117 in Pearson, Spearman, and Kendall-Tau coefficients, respectively. Besides, CodeVisionary provides detailed evaluation reports, which assist developers in identifying shortcomings and making improvements. The resources of CodeVisionary are available at https://anonymous.4open.science/r/CodeVisionary.

1 Introduction

With the rapid development of large language models (LLMs), these models have demonstrated promising results in code generation Rozière et al. (2023); Shen et al. (2023). LLM-based code tools, such as GitHub Copilot111https://github.com/features/copilot and Cursor222https://www.cursor.com/, have attracted a great number of users, effectively addressing their programming needs. Effectively evaluating the capabilities of LLMs in accomplishing code generation tasks is beneficial for identifying their shortcomings, ultimately enhancing the practical utility in real-world software development scenarios. Current approaches for evaluating LLM-generated responses in code generation can be categorized into human-centered, metric-based, and LLM-based. Human-centered approaches Evtikhiev et al. (2023) rely on domain experts to evaluate LLM-generated responses based on their professional knowledge and programming experience. Although domain experts can offer accurate evaluation, these approaches are labour-intensive and time-consuming. Metric-based approaches Papineni et al. (2002); Ren et al. (2020); Chen et al. (2021) typically require reference answers as ground truth or high-quality unit tests which are generally difficult to create, maintain, and scale across diverse programming languages Chen et al. (2024b); Jiang et al. (2024a).

Recently, LLM-based approaches Zhuo (2024); Tong and Zhang (2024) have gained increasing attention among researchers and practitioners. LLMs possess strong context-understanding and instruction-following capabilities, allowing them to perform more interpretable evaluations. Compared to metric-based approaches, LLM-based approaches have achieved outperforming performance for evaluating LLMs in code generation. However, current LLM-based approaches still face the following limitations:

(1) Lack of multisource domain knowledge: The absence of multisource domain knowledge renders LLM-based approaches inaccurate Chen et al. (2024b). Figure 1(a) illustrates several scenarios where LLM-based approaches fall short. Scenario ①: Lack of latest programming technology knowledge. When code generation tasks involve the latest programming technologies, these approaches fail to provide accurate evaluation due to a lack of relevant knowledge. For instance, a code generation task inquires about a function in “Python 3.14”, which is beyond LLMs’ knowledge. Scenario ②: Lack of visual and interaction information. When involving front-end code, these approaches cannot view or interact with the graphical interface (e.g., a personal blog homepage), leading to inaccurate evaluations. Scenario ③: Lack of runtime and linting information. Other information regarding code execution, syntax checking, and code issues is crucial for a comprehensive evaluation. Without external tools, LLM-based approaches cannot access this information Chen et al. (2024b).

(2) Insufficient comprehension of complex code: Real-world code generation tasks often involve multiple requirements, leading to LLM-generated responses that include complex and numerous code snippets. However, current LLM-based approaches struggle with comprehending and evaluating such complex code, as these code generation tasks typically require multiple reasoning steps Wang et al. (2024); Zheng et al. (2023) and necessitate a detailed evaluation of each task requirement and the corresponding code snippet. As shown in Figure 1(b), the inability to comprehend complex code poses great challenges to LLM-based approaches.

Besides, current LLM-based approaches solely provide an evaluation score without assessment details. Nowadays, the automation of code generation evaluation is being integrated into the Continuous Integration/Continuous Deployment (CI/CD) pipeline of software development Chen et al. (2024b). Real-time and comprehensive evaluation reports are essential for the rapid improvement of LLMs and better align with developers’ preferences.

Considering the limitations faced with the LLM-based approaches, we propose an LLM-based agent framework for evaluating LLMs in code generation, named CodeVisionary. The LLM-based agent framework, which can interact with the environment by invoking external tools, is capable of handling complex tasks Jin et al. (2024); Huang et al. (2023); Mao et al. (2024). Given a code generation task and the corresponding LLM-generated response, CodeVisionary evaluates the response through two stages, ultimately providing an evaluation score and evaluation report: (1) Multisource knowledge analysis stage: We first formulate a detailed evaluation plan and then collect comprehensive and multisource domain knowledge by executing the plan step by step. (2) Negotiation-based scoring stage: We employ multiple judges engaging in discussions to facilitate the comprehension of complex code and reach a consensus on the evaluation score. Besides, we consolidate the assessment details and construct a structured evaluation report.

In summary, the main contributions of this paper are as follows:

(1) We are the first to propose an agent-based framework for evaluating LLMs in code generation, named CodeVisionary.

(2) CodeVisionary evaluates LLMs through two stages, a multisource knowledge analysis stage for collecting multisource domain knowledge based on the stepwise evaluation plan and a negotiation-based scoring stage for assessing LLM-generated responses through discussions between multiple judges.

(3) We conduct thorough experiments on CodeVisionary and the results demonstrate the effectiveness of CodeVisionary across a wide range of programming languages and coding scenarios.

2 Approach

In this section, we describe the overall framework of CodeVisionary. As shown in Figure 2, CodeVisionary consists of two stages: (1) Multisource knowledge analysis stage for gathering comprehensive and multisource domain knowledge, and (2) Negotiation-based scoring stage for assessing LLM-generated responses through discussion between multiple judges. CodeVisionary utilizes LLMs as central control agents to conduct multi-turn interactions with the environment. During each interaction, the LLM agent responds with “thought” and “action”, respectively, where “thought” represents its reasoning analysis of the environment feedback and “action” represents the command to be executed. As depicted in the “Agent Runtime” part of Figure 2, the actions are executed within the environment, and the corresponding environment feedback is collected as “observation” to the LLM agent in the next interaction.

2.1 Multisource Knowledge Analysis Stage

In this stage, CodeVisionary utilizes an LLM agent to gather comprehensive domain knowledge, including the latest programming technology knowledge, visual and interaction information, and runtime and linting information. The LLM agent follows the paradigm of “construct”, “comprehend”, “plan”, and “analyze”. This paradigm mirrors the way humans address complex problems. Before solving complex problems, people typically first decompose the problem and formulate a plan, then proceed to analyze and solve the problem step by step. Recent studies Wang et al. (2023a); Jiang et al. (2024b) conclude that prompting LLMs to formulate plans before addressing problems is effective. Our designed paradigm is as follows:

Construct: This phase aims to construct a complete and executable environment, which is essential for evaluating the LLM-generated response accurately. Specifically, the LLM agent constructs the necessary environment within a Docker container based on the code generation task and the LLM-generated response. The initial Docker container is configured with network settings and our designed external tools. Constructing the environment typically involves setting up the programming environment and installing the external dependencies. Figure 2 illustrates a code generation task requiring the LLM agent to set up the “Python” interpreter and install the “Pandas” dependency for data processing. For more complex code generation tasks, additional setup of configuration files, environment variables, and other essential components is required.

Comprehend: This phase aims to enhance the LLM agent’s comprehension of the task requirements and prepare for formulating a thorough evaluation plan. Specifically, the LLM agent comprehends the code generation task and decomposes the task requirements. As illustrated in Figure 2(a), the LLM agent breaks down the code task into several detailed requirements: “Read and print file contents”, “Handle file reading exceptions”, and “Count and save occurrences of words”. Decomposing the requirements helps the LLM agent understand complex tasks by breaking them into smaller, manageable parts.

Plan: This phase divides the evaluation of LLM-generated responses into several steps, which facilitates the verification of each task requirement and reduces the reasoning burden on the LLM agent. Specifically, the LLM agent formulates a detailed evaluation plan. Each step in the plan includes a brief goal (i.e., “Goal”) and specific guidance (i.e., “Guidance”) on how to achieve the goal. As illustrated in Figure 2(a), the plan formulated by the LLM agent includes goals such as “Static Linter Analysis”, and “Dynamic Execution Analysis”, along with corresponding guidance. The goal and guidance of each step in the plan collectively specify the action that the LLM agent should take. For instance, the goal of the “Static Linter Analysis” is to ensure the LLM-generated response adheres to code syntax and style, and the guidance is to take the “linter_analysis” action. Below is a list of all possible actions during each step:

  1. 1)

    Dynamic Execution Analysis: This action checks for any compilation errors and analyzes whether the execution message aligns with the expected outcomes. Possible commands include “python test.py” for running a Python script, “gcc -o output test.c && ./output” for compiling and executing a C program, and so on.

  2. 2)

    Static Linter Analysis: This action checks for syntax errors, code issues and style inconsistencies. It helps identify potential problems in the LLM-generated responses without execution. We design the command “linter_analysis -f ‘path’” to check a file or directory for syntax compliance. This command automatically selects appropriate static analysis tools for the given file path and returns a structured checking report.

  3. 3)

    Unit Tests Analysis: This action involves writing and executing unit tests, ensuring the LLM-generated response behaves as expected under various conditions. These unit tests help analyze the functionality and reliability of the responses by providing different inputs and validating the outputs utilizing assertions. For instance, consider a function that processes a list of integers and returns a list of their squares, but only for even numbers. A unit test might provide the input “[1, 2, 3, 4]” and utilize the assertion “assert process_list([1, 2, 3, 4]) == [4, 16]” to verify that the output is as expected.

  4. 4)

    Screenshot Analysis: This action involves capturing a screenshot of the front-end code for visualization analysis. We design the command “screenshot_analsis -f ‘path’ -q ‘query’”. By providing a file path, this command will render it into a screenshot, with an analysis report generated by a multimodal LLM acting as a software expert. The LLM agent can also query the screenshot to extract relevant information, such as visual elements and layout.

  5. 5)

    Interaction Analysis: This action involves simulating user interactions with the front-end code to evaluate the interactive elements. We extend the “screenshot_analysis” command with the “-a ‘actions’” parameter to interact with the graphical interface before taking the screenshot. Possible interactions include clicking elements, filling input fields, hovering over elements, scrolling, and so on.

  6. 6)

    Web Browsing Analysis: This action involves retrieving additional information from the website, including the knowledge of the latest programming technologies and specialized answers. We design the command “web_browse -q ‘query’” to search the website according to the query.

  7. 7)

    General Semantic Analysis: Considering the LLM’s powerful contextual understanding capabilities, the LLM agent can also evaluate the functionality, logic, complexity, security, and robustness of the LLM-generated response without invoking external tools.

  8. 8)

    Bash Command: In addition to the actions designed specifically for code generation, the LLM agent also needs to call bash commands during the evaluation process to perform steps such as writing code, writing data, viewing files, and navigating the file system.

Analyze: In this phase, the LLM agent follows the evaluation plan, executing the action in each step and analyzing the corresponding execution results. We require that the LLM agent alternates between executing and analyzing during interactions, with the current state indicated using “Execute State” or “Analyze State”.

  • •

    Execute State: In this state, the LLM agent takes the actions specified in the current step (i.e. the actions illustrated in the “Plan” phase). The actions are executed in the constructed Docker container and the corresponding execution results are collected as the environment feedback (i.e. “observation”) to the LLM agent.

  • •

    Analyze State: In this state, the LLM agent takes the action “analyze_current_step” to analyze and report the execution results. We predefine different report templates for the execution results of various actions, as detailed in Appendix E.

We also provide hints as additional environment feedback based on the LLM agent’s state to facilitate the evaluation process, as shown in Picture 3. Finally, the analysis reports of each step are collected as the input for the next stage.

2.2 Negotiation-based Scoring Stage

In this stage, CodeVisionary utilizes multi LLM agents to act as judges, scoring the LLM-generated response through discussions. This negotiation strategy helps mitigate inaccuracies and biases in LLMs’ comprehension of complex code, ensuring a more comprehensive evaluation through diverse perspectives and consensus among judges.

2.2.1 Definition of Judges

Let A1,A2,…,AnA_{1},A_{2},\ldots,A_{n} represent the nn LLM agents acting as individual judges. Each judge AiA_{i} is responsible for scoring the LLM-generated response based on the analysis information in Section 2.1 and the evaluation criteria. The evaluation criteria include code correctness, functionality, and clarity, as detailed in Appendix C. Each judge provides an evaluation score SiS_{i} and corresponding scoring reason RiR_{i} for their evaluation. Formally, we define judge AiA_{i} as a tuple:

Ai=(Si,Ri)A_{i}=(S_{i},R_{i}) (1)

where SiS_{i} and RiR_{i} denote the score and reason provided by the judge AiA_{i}, respectively.

2.2.2 Negotiation and Scoring

After each judge AiA_{i} has provided their initial score Si0S_{i}^{0} and reason Ri0R_{i}^{0}, their evaluations are shared among all other judges. This ensures that each judge is aware of the scores and reasons provided by their peers. Formally, this process can be represented as:

∀i,j∈{1,2,…,n},(Si0,Ri0)→Aj\forall i,j\in\{1,2,\ldots,n\},\quad(S_{i}^{0},R_{i}^{0})\rightarrow A_{j} (2)

Then these judges engage in multiple rounds of discussion to reach a consensus. Formally, let kk denote the round number. In each round kk, each judge AiA_{i} can take one or more actions A​c​t​i​o​nikAction_{i}^{k}, where:

Here, “Maintain(Explanation)” refers to keeping the current score along with the reason. Conversely, “Change(S_i, R_i, Explanation)” means changing the current score along with the reason. “Query(A_j, Explanation)” indicates querying judge AjA_{j}’s score. Besides, these judges are required to provide explanation while taking different actions. After each round kk, the current score and reason of each judge, as well as the actions taken, are shared among all judges:

The negotiation ends when either the number of rounds is exceeded or all judges reach a consensus. The final evaluation score is calculated as the average of the scores provided by all judges:

2.2.3 Evaluation Report Generation

We obtain the environment configuration, task requirements, and stepwise analysis reports in Section 2.1 and the final evaluation score in Section 2.2.2. Besides, CodeVisionary leverages another LLM agent to conclude the overall evaluation results, which consist of the evaluation reasons provided by multiple judges in Section 2.2.2 and the optimization suggestions. Then the LLM agent generates the initial evaluation report in Markdown format. To enhance readability, we standardize and beautify the initial evaluation report. We utilize Prettier333https://github.com/prettier/prettier to check for formatting issues and maintain a consistent style. Besides, we employ Pandoc444https://github.com/jgm/pandoc to convert the Markdown report to PDF format.

3 Experiments

3.1 Datasets

CodeArena Yang et al. (2024a) is a human-curated benchmark of 397 high-quality code generation tasks, covering various coding scenarios and programming languages. It simulates the complexity and diversity of real-world tasks, with each task classified as “easy”, “medium”, or “hard” based on complexity. To evaluate CodeVisionary’s performance across diverse and complex tasks, we filter CodeArena, generate responses using different LLMs, and manually score the responses. The filtering, response generation, and manual scoring process is as follows:

  1. 1)

    Filtering: We first retain tasks classified as “hard”. Then, we filter out tasks that depend on specific software or platforms, such as MATLAB and Verilog.

  2. 2)

    Response Generation: We generate responses for each code generation task utilizing three popular LLMs, including GPT-3.5-turbo555https://openai.com/index/gpt-3-5-turbo-fine-tuning-and-api-updates/, Claude-3.5-Sonnet666https://www.anthropic.com/claude/sonnet, and GPT-4o777https://openai.com/index/hello-gpt-4o/.

  3. 3)

    Manual Scoring: Each code generation task and corresponding LLM-generated response is scored by two experienced experts ranging on a scale from 0 to 4, following the widely-used evaluation criteria Evtikhiev et al. (2023) described in Appendix D. In case of scoring discrepancies, a third expert is introduced to adjudicate. All experts possess over 5 years of code generation experience. Besides, they are unaware of the LLM corresponding to each LLM-generated response.

The statistics of our constructed benchmark are illustrated in Table 1. Each sample is represented as a triplet: (code generation task, LLM-generated response, score).

3.2 Comparison Baselines

To evaluate the performance of our framework, we compare the state-of-the-art LLM-based approaches. Following the previous work Tong and Zhang (2024), we also introduce a vanilla approach as the baseline.

  • •

    VANILLA Tong and Zhang (2024) directly prompts LLMs to determine the correctness and helpfulness of the LLM-generated response.

  • •

    ICE-Score Zhuo (2024) utilizes assessment criteria and evaluation step template to evaluate the LLM-generated response’s usefulness and functional correctness.

  • •

    CODEJUDGE Tong and Zhang (2024) guides LLM in performing “slow thinking” to arrive at an in-depth and reliable evaluation of semantic correctness.

3.3 Evaluation Metrics

We follow best practices in natural language generation (NLG) evaluation and utilize Kendall-Tau (τ\tau), Pearson (rpr_{p}), and Spearman (rsr_{s}) coefficients to measure the correlation between evaluation scores assigned by different approaches and the ground truth (i.e. scores annotated by humans) Zhou et al. (2023); Zhuo (2024).

3.4 Experimental Results

We compare CodeVisionary with the three baseline methods using three evaluation metrics (i.e. rpr_{p}, rsr_{s}, and τ\tau). Experimental results are shown in Table 2. We observe that CodeVisionary consistently outperforms all the baseline methods across three LLMs (i.e. responses generated by GPT-3.5-turbo, Claude-3.5-Sonnet, and GPT-4o). Overall, CodeVisionary achieves average scores of 0.286, 0.248, and 0.217 on rpr_{p}, rsr_{s}, and τ\tau, respectively, outperforming the best baseline methods with improvements of 0.202, 0.139, and 0.117. These improvements are due to CodeVisionary’s ability to collect multisource and comprehensive domain knowledge and provide the evaluation score through negotiation. We observe that state-of-the-art LLM-based approaches, ICE-Score and CODEJUDGE, show little difference compared to VANILLA, indicating that current LLM-based methods struggle to comprehend complex code. Besides, CodeVisionary’s performance declines when evaluating responses generated by GPT-4o, probably because GPT-4o is leveraged as the control agent in CodeVisionary, which may introduce self-enhancement bias Zheng et al. (2023).

3.5 Ablation of CodeVisionary

To explore the impact of different components on the performance of CodeVisionary, we construct two variants: one without the multisource knowledge analysis stage (i.e. w/o MKA) and one without the negotiation-based scoring stage (i.e. w/o NS). The first variant follows a completely free evaluation process instead of comprehending the task and formulating the step-by-step evaluation plan. The second variant scores the LLM-generated response multiple times and takes the average instead of discussion between multiple judges. As shown in Table 3, the addition of the MKA and the NS stage achieves higher performance on rpr_{p}, rsr_{s}, and τ\tau across all three LLMs. Specifically, adding the MKA stage improves the metrics by 0.074, 0.054, and 0.036 on average, respectively. The MKA stage excels in understanding complex task requirements and formulating detailed evaluation plans, thereby ensuring the thorough collection of multisource domain knowledge. Similarly, adding the NS stage improves the metrics by 0.065, 0.068, and 0.070 on average, respectively. The NS stage leverages multiple judges for negotiation, mitigating inaccuracy of comprehending complex code and integrating diverse opinions.

3.6 Performance about Programming Languages and Coding Scenarios

Figure 4 illustrates the performance of CodeVisionary across the Top-5 programming languages and coding scenarios by the number of samples. As shown in Figure 4(a), CodeVisionary demonstrates superior performance in C++, achieving rpr_{p}, rsr_{s}, and τ\tau scores of 0.716, 0.673, and 0.627, respectively. Besides, CodeVisionary excels in JavaScript probably due to “Screenshot Analysis”, which converts front-end code into visual screenshots. Figure 4(b) highlights that CodeVisionary stands out in the “User Interface and User Experience” and “Emerging Technologies and Applications” coding scenarios, achieving rsr_{s} scores of 0.505 and 0.469, respectively. This performance is attributed to “Interaction Analysis”, which simulates user interactions with the graphical interface, and “Web Browsing Analysis”, which retrieves the latest technologies, compensating for potential knowledge gaps in LLMs.

3.7 Case Study of Evaluation Reports

Figures 5 and  6 in Appendix F illustrate two examples of evaluation reports generated by CodeVisionary. Both examples utilize “Bash commands” to write files, “Static Linter Analysis” to check code syntax, and “General Semantic Analysis” to assess functionality. For the first example, “Screenshot Analysis” and “Interaction Analysis” dynamically check the colour changes of the button under different operations, providing a multimodal analysis. For the second example, “Dynamic Execution Analysis” and “Unit Tests Analysis” are leveraged to evaluate the correctness and robustness of the response under regular and edge inputs. Besides, the “Overall Evaluation Results” information provides developers with comprehensive insights and potential improvement.

4 Related Work

4.1 Evaluating LLMs in Code Generation

Early works directly transfer evaluation metrics from the natural language processing (NLP) domain to code generation, such as BLEU Papineni et al. (2002), ROUGE Lin (2004), and METEOR Banerjee and Lavie (2005). However, these metrics fail to capture the syntactic and functional correctness. To mitigate the limitation, CodeBLEU Ren et al. (2020) incorporates syntactic and semantic information from Abstract Syntax Trees (AST) and Data Flow Graphs (DFG). Recently, execution-based metrics have gained prominence, including pass@k Chen et al. (2021), and pass@t Olausson et al. (2024). However, these metrics are based on high-quality unit tests and are limited to executable code.

For more complex and diverse tasks Bairi et al. (2024); Shrivastava et al. (2023), human-centered approaches become particularly important. Human evaluators can provide reliable and accurate evaluations based on their professional knowledge and programming experience, which are also essential for fine-tuning LLMs to better align with human preferences Ouyang et al. (2022). However, human-centered approaches are labour-intensive and time-consuming. Recently, LLM-based approaches leverage LLMs to simulate the human evaluation process, enhancing efficiency and scalability. ICE-Score Zhuo (2024) aligns well with human preferences in terms of code accuracy and functionality without test oracles or references. CODEJUDGE Tong and Zhang (2024) employs a “slow thinking” approach, enabling a thorough and reliable assessment of code’s semantic correctness.

4.2 LLM-Based Agents

AI agents are artificial entities capable of accomplishing complex tasks by perceiving the environment and taking actions Xi et al. (2023); Liu et al. (2024). Recently, rapid progress in LLMs has greatly increased researchers’ attention to LLM-based agents Chen et al. (2024c); Qiao et al. (2024).

LLM-based agent frameworks leverage LLM as the central controller to address complex tasks by integrating external tools and powerful understanding capabilities of LLMs. LLM-based agent frameworks designed for software engineering have demonstrated superior performance across various software development and maintenance tasks, including requirements engineering Jin et al. (2024); Arora et al. (2023), code generation Huang et al. (2023); Ishibashi and Nishimura (2024), static bug detection Mao et al. (2024); Fan et al. (2023), code review Tang et al. (2024); Rasheed et al. (2024), unit testing Yuan et al. (2023), system testing Yoon et al. (2023); Deng et al. (2023), fault localization Qin et al. (2024); Wang et al. (2023b), program repair Bouzenia et al. (2024), end-to-end software development Yang et al. (2024b); Zhang et al. (2024) and end-to-end software maintenance Chen et al. (2024a).

5 Conclusion

This paper focuses on evaluating LLMs in code generation and proposes a novel agent-based framework, named CodeVisionary. CodeVisionary consists of a multisource knowledge analysis stage for gathering multisource domain knowledge based on the stepwise evaluation plan and a negotiation-based scoring stage for employing multiple judges engaging in discussions to better comprehend complex codes, finally reaching a consensus on the evaluation score. Besides, we provide detailed evaluation reports assisting developers in identifying shortcomings. Compared with the state-of-the-art approaches, the experimental results validate the effectiveness of CodeVisionary. In the future, we intend to further evaluate CodeVisionary on a broader range of datasets.

6 Limitations

Dataset Validity Concerns: The scope of the constructed benchmark is limited and may not cover all coding scenarios. Hence, the experimental results based on this benchmark may not be fully generalizable. In future research, we intend to extend our investigations to more coding scenarios.

Result Variability: Due to CodeVisionary relying on LLM agents for evaluating and scoring the LLM-generated response, the experimental results exhibit variability. We therefore conduct multiple trials and average the results to obtain a more stable measure.

Appendix A Experimental Details

CodeVisionary and the baseline methods are provided access to GPT-4o. The sampling temperature for the LLMs used in CodeVisionary is set to 0.2. For the multisource knowledge analysis stage, we limit the maximum number of interactions to 40. For the negotiation-based scoring stage, we set the number of judges to 3 and allow up to 5 rounds of negotiation. Our implementations of baseline methods are based on https://github.com/terryyz/ice-score/ and https://github.com/VichyTong/CodeJudge.

Appendix B Correlation Metrics

For all correlation metrics, we use the implementation from https://scipy.org/ and call these APIs with the default settings.
